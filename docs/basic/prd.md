# 产品逻辑说明

## 问题与目标

目标是增强 Agent 的产品判断、交互设计、实现和验证质量，同时避免留档流程接管任务。

## 定位

Open VibeCoding 是面向 Agent 的能力框架，而不是 PRD 生产流水线。它在产品、交互设计、研发、测试和 Vibe Coding 增强五个领域提供场景 Skill、可组合 CLI 工具与必要的非阻断提醒。用户直接描述目标；Agent 依据当前任务与证据自主选择能力。

## 用户问题

- 模糊的产品问题容易被过早翻译成开发清单。产品诊断先判断战略、范围、结构、框架或表现层问题，再决定是否需要实现。
- 交互方案确定前直接写界面，常导致高成本返工。大界面可先生成不同方向的效果图供评审，再以参照图和真实截图作视觉对比。
- 固定留档流程会夺走 Agent 的规划空间。Open VibeCoding 不把 requirement、PRD、change 或 tasks 当任务前置材料，也不在后台自动补写。
- 单靠构建成功不足以说明结果可靠。测试策略按风险提醒 Agent 选取最小足够证据，并区分通过、失败与未验证。

## 用户故事

- 作为用户，我可以直接描述产品问题或开发目标，不必先选择固定命令或填写 PRD。
- 作为设计评审者，我可以先比较不同交互/视觉方向，再用真实截图判断落地质量。
- 作为开发者，我希望 Agent 自主拆解任务，并只在风险需要时保留验证证据。

## 产品原则

1. 先诊断场景，再组合能力；五个领域不是阶段门。
2. Agent 管理自己的思考和任务分解，CLI 只承担确定性动作。
3. 代码是默认实现说明；产品文档、设计稿和审查界面仅在用户要求或交付确有需要时制作。
4. 只保留无法从代码可靠重建的关键证据。历史 `.open-vibecoding/` 资料只读，不推断、迁移或回填。
5. 外部事实需要来源，用户可见体验需要真实验证；安全与权限仍由宿主规则和用户授权决定。

## 能力范围

五域与统筹关系见 [Open VibeCoding 架构](./open-vibecoding-architecture.md)。产品层目前提供产品五层诊断、benchmark 来源治理及按需调研；交互层提供信息架构/流程判断、设计方向和视觉对比；研发层提供 Agent 自主实现所需的 CLI 与运行态；测试层提供按风险验证和质量诊断；增强层提供客户端适配、hooks、画布、学习与知识复用。

## 功能范围

包含五域场景路由、能力目录、客户端集成、设计与视觉证据工具、运行态和质量检查，以及既有历史资料的只读查看。不包含自动生成或推进 PRD、change、tasks。

## 验收标准

新初始化不创建 PRD 草稿、change、任务图或旧版版本快照；旧生成/推进命令明确返回移除信息；历史查看仍可用；客户端适配与测试保持通过。

## 维护规则

修改能力边界时更新对应 Skill、能力目录、用户文档和测试。历史记录不根据当前代码回填。新增文档必须服务用户交付或必要协作，而非流程留痕。

## 非目标

不恢复旧版 `capture -> classify -> synthesize -> review -> change -> tasks` 固定流程；不为了留痕自动创建 PRD、change 或任务文件；不要求用户先选择 `/from-idea` 一类入口；不以历史材料缺口阻断当前任务。
