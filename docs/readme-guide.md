# README and public visuals

Open with a sentence that says who uses Open VibeCoding and what they can get done. Then show how to install it in a project, give the reader a first task to try, and link to the documentation for details.

## README structure

1. Product name, one-sentence purpose, supported agents, language switch, and a link to Releases.
2. One hero image showing how a goal becomes an implementation and verification result.
3. A tested install command and a realistic first task. Use the exact GitHub Release asset name.
4. A short table of tasks and outcomes. Keep command options, compatibility details, and architecture in linked guides.
5. Keep the Chinese and English entry points aligned on capabilities, requirements, and release version. Link each one to its own gallery.

## Visuals

- Use warm ivory for the canvas, dark forest for structure, and sage or terracotta for emphasis. Current reference colors are `#F7F3E8`, `#21493D`, `#597A62` and `#C46A37`.
- Keep the banner wide enough to leave room for the quick start. Icons should still read at narrow GitHub widths. Put explanation and alt text in the README. Localize any text embedded in an image.
- Use screenshots from actual runs when demonstrating interface behavior. Keep customer details, system paths, access tokens, and image metadata out of published assets.
- Before publishing, open both READMEs on GitHub and check the banner, links, code blocks, and language switch. Check that a clean install can complete the quick start and that the default knowledge bindings are empty.
