# 视觉实现与对比

本 Skill 负责把已明确的用户任务、交互规则和视觉方向落实为真实界面，再检查实现是否达到预期。流程与状态未定时用 `$open-vibecoding-interaction-design`；大界面仍需比较候选方向时用 `$open-vibecoding-visual-direction-review`。轻量样式优化不机械升级为三方向评审。

## 实现判断

1. 看当前页面、消费组件、项目设计系统和用户给的参考。已有界面默认继承字体角色、色彩、密度、表面与图标语言；除非用户要换风格，不把它重做成另一个产品。
2. 写清本次界面的用途、目标用户、核心动作、约束和一个记忆点。检查事实与素材是否真实；缺少关键事实、品牌图或内容图时先核验或说明降级，不用装饰掩盖缺口。
3. 优先沿用现有结构。空白页面且主题、模块明确时才按需用 `design-starter` 和 `.open-vibecoding/design/` 模板；模板是起点，不高于用户提供的设计稿或真实界面。
4. 在实现中检查信息层级、字体角色、色彩、空间、表面、图标和动效是否服务用户任务。避免无依据的蓝紫渐变、等权白卡堆叠、默认字体和只换颜色的伪方向。
5. 对 logo、icon、avatar、badge、贴纸、空态插画和单物件 UI 位图，先检查原始素材及消费组件。`transparent-cutout` 要透明背景和四角；`opaque-full-bleed-tile` 要四边四角不透明、无烘焙圆角或白边。UI 容器的圆角、边框和阴影通常留在代码中。细节见 [设计资产合同](references/design-asset-contract.md)。
6. 新入口、导航、按钮和空态主动判断并补齐合适图标；用 `$open-vibecoding-icon-system` 继承现有家族，按需检索、设计 SVG 或原生生成位图，并检查同组视觉重量与风格。来源、许可和透明化方法由对应子能力维护。

## 实际验收

- 对新界面或大幅修改，保留选定参考与真实实现的同视口、同状态对比；可用 `visual-prepare` 整理参考，`visual-compare` 生成证据。候选效果图不等于已实现界面。
- 对按钮、间距、字体或单组件等轻量调整，优先做局部前后对比；构建通过和单张截图不能替代用户可见变化的视觉证据。
- 同构列表、卡片、网格和表格不仅检查外框，还检查标题、描述、状态、按钮、图标等同槽位对齐。单物件需要判断视觉重心时，检查画布中心、主体边界和视觉重心，不凭主观感觉宣称居中。
- 检查真实控件中的文案、截断、可访问性名称和已有多语言；用户可见文案说明能做什么、会发生什么和下一步。
- 生成了视觉证据板时，在最终回复中直接嵌入工具返回的 `chatEmbed`，让用户能看到证据。

## 留底边界

只有视觉候选、用户选中的参考、像素合同、实际截图或比较结果需要跨轮复核时，才保存相应 `.open-vibecoding/design/active/` 文件。保存时标明当前任务和来源，不让旧任务方向静默变成新任务默认值。产品事实、方向计划、素材清单和设计说明不是每次界面任务的固定前置文档；代码仍是默认实现说明。

需要内置主题、布局和组件库时按需读 `.open-vibecoding/design/README.md`；需要判断三方向差异时读 [方向引擎](references/direction-engine.md)，但由独立方向评审场景负责产生候选。
