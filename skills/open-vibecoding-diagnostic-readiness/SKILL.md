# 修复与优化后的诊断补强

归属研发，供测试与线上异常分析复用；无需用户再提醒“加日志”。根据本次失败或性能问题判断适用性，不按固定关键词匹配，不作为所有改动的必经流程。

## 让下一次问题可继续定位

修复或优化时主动问：如果相同现象再出现，现有证据能否判断卡在哪一步、为什么、影响哪个版本与哪次操作？先读项目已有日志、测量与采集方式。够用就复用；不足时将针对本次问题的最小诊断补强纳入已授权实现。只读诊断仍保持只读，指出缺口和建议，不借此修改代码。

按尚未能区分的候选原因选择记录点，而不是逐行打印或输出全部数据。例如多阶段任务区分提交、受理、执行与结果保存；异步或跨端流程复用适合的操作关联标识，使记录能串联。失败时保留安全的错误类别、必要状态与原因上下文；不要让一个笼统提示抹掉全部原因，也不要把这些开发诊断直接展示给普通用户。

性能优化按具体瓶颈记录总耗时、相关阶段耗时与必要工作量，区分等待、执行、重试或取消。用可比较的输入、版本、环境和测量口径核对前后变化；单次更快不代表所有场景改善，不能为了测量再次制造高负载。

## 证据能取得，才算补强生效

测试复用已有安全环境验证代表性路径，读回实际输出，检查关键字段、操作关联和最终结果是否一致；异常或慢路径能安全验证时验证，不能验证时明确边界，不在生产制造故障。能编译、代码里有日志或已有平台连接，都不等于记录已经产生。

检查后续排查者在哪里取得日志、如何限定到本次操作。控制台复制不应只剩折叠的 Object；按项目方式提供可复制的脱敏字段或现有导出入口，不强制统一 JSON 格式或另建报告。日志记录失败不应改变原业务结果或掩盖原始故障。

## 控制副作用与跟进边界

- 复用既有日志设施和配置；不为此强制安装 SDK、搭平台或增加对外上报。涉及外部工具用法时按项目调研规则核验。
- 只记录必要上下文，脱敏并限制长度；不输出凭证、完整用户内容、媒体或带敏感参数的地址。高频路径考虑等级、采样、限频和既有轮转，避免日志本身造成性能、磁盘或成本问题。不静默全局开启 debug。
- 临时详细诊断应有关闭方式与适用范围；保留关键长期证据，不在收尾时删掉下次仍需使用的诊断点。不擅自清除历史记录。
- 当前任务内主动读回验证。上线效果复查用 `$open-vibecoding-production-anomaly-analysis`，先确认包含改动的版本已在目标环境生效；没有复发不等于证明修好。
- 持续后台跟踪仅在已有明确授权和可用调度时执行，明确范围、通知与结束条件；否则交代缺口，不承诺后台自我监控。补强不扩大部署、付费调用、外部写入或账号查询权限。

交付用简短业务语言说明补了什么、已验证什么、下次在哪里查及剩余盲区；既有证据足够时说明复用了什么。不为留痕生成 PRD/change/tasks 或诊断文档。
