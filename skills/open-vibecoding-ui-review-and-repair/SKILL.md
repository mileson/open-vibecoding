# Review 并修复

本场景组合 `$open-vibecoding-ui-interaction-review` 与 `$open-vibecoding-debugging`。Review 的操作方法和问题格式以独立审查 Skill 为准，修改方法复用研发能力；这里仅负责交接、角色独立性、复查与结束条件。能力目录的 `uses` 声明复用关系，Agent 自己管理执行进度。

## 角色与启动

- 用户希望完成检查、修复和复查时采用本场景；仅要求分析或 review 时，调用独立 Review 后交付结果。不要因出现某个词自动获得修复授权。
- 主 Agent 确定目标页面、用户任务、运行环境及可用测试数据。以宿主 subagent 工具启动独立 reviewer；待有可行动问题时再启动另一个 fixer。Reviewer 与 fixer 不能是同一个 Agent，也不能让 fixer 自己签认修复完成。
- 初次 reviewer 接收最小产品目标和约束；fixer 接收问题证据与本次负责的文件或模块。告诉 fixer 当前代码库可能有其他人的改动，保留已有修改，只处理分配范围。
- 复用 reviewer、fixer 和任务专用浏览器会话，按 review、修复、复查顺序交接操作权。不同 Agent 不同时点击同一个界面；实现过程中 reviewer 不对正在变化的版本下结论。

## 问题交接与复查

1. 主 Agent 接收独立 Review 的问题与覆盖缺口，过滤重复项及无依据建议。Fixer 只修复有证据、且在用户目标内的问题；需要新产品决策的建议列为待定，不擅自扩大功能。
2. Fixer 先定位根因，再修改并做对应代码验证。返回问题标识、改动位置、验证结果和剩余不确定性。修改完成不等于问题已解决。
3. 让运行环境加载本轮实际变更，再由 reviewer 在同一用户角色、数据和状态下重新走原复现路径，检查相邻路径是否回归。用新截图或观察证据关闭问题；未复测的修复保持未确认。
4. 仍有本轮范围内的明确问题时，把复查结果交回 fixer。后续轮次优先复查改动与相关路径，只有新发现表明影响扩大时才扩展覆盖。

## 停止与交付

用户给了轮数或时间预算时沿用；未给预算时默认最多三轮修复与复查。若同一阻塞重复、连续两轮没有减少问题，或继续需要新的用户选择，结束本次迭代并说明原因，保留剩余问题；不要反复重启环境或不断 spawn 新 Agent 硬试。

原问题均已实际复测通过、相邻关键路径通过，且范围内没有未解决的阻断问题时，才声明本次目标完成。额度用完、工具不可用或有未覆盖状态时按实际范围交付部分结果。

交付包括修复与复测结果、未解决或未验证项、实际覆盖范围。落实 `$open-vibecoding-visual-evidence-delivery`，在最终回复嵌入 reviewer 本轮复测的实际截图；有确认稿时展示确认稿与实际结果，无确认稿时展示最终实际界面。截图无法取得则标记视觉未验证。不为迭代创建固定任务文档。结束前释放本任务的浏览器操作权并清点自建进程或会话；只关闭本任务不再需要的资源。
