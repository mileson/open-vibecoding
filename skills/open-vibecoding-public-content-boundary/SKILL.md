# 用户可见内容边界

内部增强子能力，由交互设计、研发、产品文档与测试共同复用。根据内容用途与受众判断，不以固定关键词、黑名单或文字扫描零命中作为通过标准；不要求用户主动调用，不新增必填表或流程文件。

## 先分清这句话给谁看

- 给 Agent 的设计约束、开发策略、测试安排、生成工具、审查标准、制作过程和内部执行状态，用于指导工作；不能顺手写进产品页面、效果图、文章、图注、页脚、字幕、口播或下载附件。
- 成品文字面向实际使用者，表达业务对象、可采取的动作、必要状态、结果和下一步。普通用户不需要知道 Agent 如何组织开发或为什么选择某种写法。
- 判断每句话：它帮助用户完成什么？删除后是否影响理解、选择、操作、安全或恢复？若只是在解释作者如何制作、系统如何实现，或重复按钮已讲清的事，默认删除整句，不为填满空间再补一句。
- 用户明确要求解释制作过程或内部规则时，写入指定文档及明确范围；仅说“写个教程”或“出个效果图”不代表授权添加制作自述。真实技术教学、开发者产品的必要技术对象按受众用途判断，不因技术词本身删除。

## 让边界进入生成输入

- 写代码、文案或生成图片前，先确定可见文字及其业务用途，将其与给工具的布局、风格、实现和验证要求分开。传给生图工具的工作指令不能变成图上的标签；图中只呈现本次需要的产品文字。
- 使用模板、组件、外部工具或委派任务时，同样传递这条边界。模板里的注释、内部字段和占位说明不能作为界面文案直接渲染。
- 不主动添加“由某工具生成”“仅供展示”“模拟已完成”“为本次视频设计”等制作身份或创作自述。这些是例子，不是穷举禁词；换成同义句、移到角落、附件名或另一语言仍需按原义检查。
- 不通过删掉说明把未知数据、生成效果图或未发生的操作包装成真实业绩、实际截图或成功回执。事实不成立时修正主张、内容或实现；实际执行与验证缺口向委托用户如实说明，不用成品角标代替核验。

## 保留真正有用的信息

| 场景 | 判断与处理 |
| --- | --- |
| 评价弹窗已有“去商店评价”，底部又写“将在新标签页打开评价页面” | 若没有额外操作条件或风险，删除重复解释；不再换一句小字补位 |
| 商店图显示“模拟已完成”，视频角落写“效果示意 · 同一照片” | 移除制作标签，检查业务表达本身成立；不改称真实客户成果 |
| 文章写“为了让读者更容易理解，我们采用……” | 直接讲内容或案例，省去作者的编排自述 |
| 页面写“根据开发规范复用组件”“已按设计规则统一样式” | 属于内部工作说明，不进入用户界面 |
| 上传需等待、保存失败需重试、删除会造成数据丢失 | 保留必要进度、失败恢复和后果，使用业务语言表达 |
| 用户明确要制作方法文档，或技术产品确需配置某个接口 | 在指定文档或实际操作所需位置说明，不扩散到其他成品 |

## 检查实际交付，而不只检查源码

- 生成后逐项阅读可见内容；界面看实际运行状态，效果图打开原图，文章检查正文与附属文字，导出材料打开最终文件。涉及多语言时覆盖已有支持语言；涉及声音时按当前任务范围听查最终音轨。
- 检查容易漏掉的角落：页脚、提示气泡、空状态、成功提示、图例、图片文字、替代文本、可复制提示词、公开文件名和附件。仅修改 Markdown 或字符串，不证明图片、网页和导出已经更新。
- 发现问题先修正来源：组件、文案、模板或生成输入，再重新检查派生结果；复查同一任务中使用相同模式的其他页面和同组产物，不只修用户圈出的那一处。
- 只读审查时报告具体内容、出现位置与用户影响；已授权修改时修正后交付。无法查看实际结果时明确该部分未验证，不宣称整套成品已通过。
- 涉及实际界面视觉时复用 `$open-vibecoding-visual-evidence-delivery` 展示本轮截图。检查结论可以留在对话中，不为证明遵守规则把检查说明重新写进成品。
