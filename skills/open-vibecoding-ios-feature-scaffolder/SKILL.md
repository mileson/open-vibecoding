# 搭建 iOS 功能骨架

用户要求在已有 iOS 项目中搭建新功能或复用组件时使用。先确认交付范围和预期入口。只做方案时保持只读，获准实现后再创建文件或修改接入点。用户同时要求落实业务行为时，按需组合 `$open-vibecoding-feature-implementation`。

1. **找到已接入的参照。** 读取目标项目约定和与需求最接近的现有模块，沿真实调用点找到所属 Target、文件组织、界面框架、状态归属、依赖注入和导航方式。样例有冲突时，优先核对同一 Target 的第二个模块和实际构建配置。若仍无法判断且会影响结构或接入，再向用户澄清。
2. **确定最小文件集合。** 区分可复用组件和业务功能模块，按本次需要选择视图、状态、模型、服务与资源。只有现有调用模式和需求确实需要时才增加配置对象、回调、ViewModel 或扩展。已有类型与依赖优先复用，文件名和访问级别跟随邻近代码。判断示例见[模块参照与接入检查](references/project-patterns.md)。
3. **生成并接入。** 按项目维护源码与资源的方式添加文件，核对是否进入正确 Target 或 Swift Package。只有交付包含接入时才修改现有调用点。沿用当前模块的主题、语言资源组织与最低部署版本；新增用户可见文案时同步项目已支持的语言，按需参考 `$open-vibecoding-ios-localization`。
4. **核验骨架。** 复查新增文件、引用和接入范围，使用项目已有构建入口验证受影响的 scheme 或 Target。根据风险检查相关测试；需要开启模拟器时遵循宿主资源规则。交付说明参考模块、实际生成与接入的文件、已做的检查以及尚未验证的事项。

骨架内使用可解析的项目类型和明确的接口。缺少业务定义时留出清晰边界并在交付中说明，避免用虚构数据、空实现或占位文案制造功能已可用的印象。
