# 运行单元测试、报告与按需修复

## 运行并报告

1. 从仓库规则、脚本、测试目标或 CI 核对命令、工作目录及选中的测试。使用任务允许的测试环境和数据。复用已有环境，控制并发和运行范围。先运行目标用例，再按用户范围和风险扩展。生成用例由 `$open-vibecoding-unit-test-generation` 处理。
2. 保存测试运行器的退出状态、结果和原始日志位置。使用运行器的结构化结果或明确汇总区分通过、失败、跳过、取消、未执行和未知数量。零个用例、命令失败或环境阻塞不能算通过。只要求运行和报告时无需编辑源码或测试。
3. 区分产品缺陷、测试缺陷、环境或工具故障、偶发失败、预期不明。单次失败和超时不足以证明产品缺陷。尽量缩小重现范围，记录预期、实际和支持归因的证据。

## 用户要求修复时

1. 只修理任务范围内、预期明确且稳定复现的问题。复用 `$open-vibecoding-debugging` 和 `$open-vibecoding-code-quality`。先保留能暴露缺陷的失败用例及日志，再做最小改动。测试本身有错时单独记录依据，不能通过放宽断言、删除用例或改写已确认预期取得通过。
2. 用相同断言、输入和可比环境重跑失败用例，再跑受影响的相关回归。修复后的通过结果和基线分别保留。受影响的真实用户路径按项目规则和测试策略验证。
3. 每个问题默认最多两轮修复。重复遇到同一阻塞、无法确认预期，或需要扩大修改范围时，交付当前证据和剩余问题。提交、推送和部署分别遵循当前任务的授权。

## 报告字段

- 项目与模块、测试类型、环境、运行命令、目标范围和原始证据位置。
- 各次运行的退出状态及实际通过、失败、跳过、取消数量。没有执行时写明原因，缺失统计写未知。
- 每个失败的预期、实际、分类与依据。修复模式另记修改位置、修复前结果、同用例复测及相关回归结果。
- 尚未覆盖的范围和未解决问题。保留脱敏证据，敏感内容从日志摘要和可分享报告中剔除。
