# 制定策略并生成用例

1. 先读 `$open-vibecoding-test-strategy`。根据需求、改动范围和实际用户路径，确定用户最终要得到什么、失败有什么后果、哪些行为和环境最值得测。复用项目的测试入口、相邻用例和夹具。需求有歧义时，区分已确认的预期与待确认项，继续完成依据明确的用例。
2. 按所选测试层产生用例。每条给出稳定 ID、初始状态与输入数据、操作步骤、可观察的预期结果和关键断言。关键断言写清检查对象、观测位置和比较条件。按风险覆盖正常、边界、失败恢复和已知缺陷，优先保留能发现实际问题的用例。
3. 按授权交付。如果只要用例，交付用例清单并标明未运行。若明确要求实现测试，沿用项目已有测试入口编写脚本，保留用例与框架测试的标识对应。只有任务授权执行时才运行测试，并沿用现有 CLI、CI 和报告约定，分别记录通过、失败、环境阻塞和未运行。功能改动的实现与验收按各自授权处理。

## 按测试层交接

| 测试层 | 处理方式 |
|---|---|
| 单元 | 用 `$open-vibecoding-unit-test-generation` 细化局部业务规则、状态变化和边界。获准实现测试时，用它生成单测脚本。 |
| 组件 | 沿用同类组件的测试框架，检查输入、交互反馈与组件向外传递的值。 |
| 接口或集成 | 沿用项目框架和现有夹具，检查实际响应、持久化、调用方收到的数据或其他副作用。 |
| 端到端 | 从真实用户入口设计到最终结果的路径。获准实现时，Web 沿用项目的 Playwright，原生端沿用项目的 Maestro 或已有测试执行器。执行与报告沿用 `open-vibecoding test-report e2e` 或项目现有入口。 |

把同一条业务规则放在足以证明它的层。若低层只能检查局部状态，而成败取决于跨入口或返回页的数据，再补端到端。工具或环境缺失时记下缺口，保留可执行的用例设计。

## 交付 JSON 和 HTML 用例清单

需要可复用的用例交付时，先写 JSON。顶层包含 `project`（标题）、`scope`（范围）、`summary`（一句话说明本次最该验证的功能结果）和 `cases`。

- 每条用例包含 `id`、`feature`（功能或场景）、`title`、`layer`、`priority`、`input`（准备数据与初始状态）、`steps`、`expected` 和 `assertions`。`steps` 与 `assertions` 分别是非空的字符串数组。
- `layer` 使用 `unit`、`component`、`api` 或 `e2e`。`priority` 使用 `high`、`medium` 或 `low`。已选定测试工具或执行目标时可填写 `target`。
- `id` 在清单内唯一，以英文字母或数字开头，可包含点、下划线或连字符。后续脚本和执行清单沿用同一个 ID。框架自带不同标识时，在现有执行报告的用例定义中保存映射。HTML 用例清单只展示计划，执行状态与实际值由已有报告链路记录。

运行以下命令校验 JSON 并渲染离线文件，交付实际生成的 HTML 和对应 JSON。

```sh
open-vibecoding test-report render --kind cases --data cases.json --out cases.html
```

## 执行前准备并核对测试数据

读取将要执行的用例中 `input` 所要求的固定数据、账号角色、权限、初始业务状态和测试环境。先查看项目已有的 fixture、seed、测试账号、准备命令及 CI 入口，优先复用能重置到相同状态的方式。缺少入口且任务明确授权实现时，按项目规范补最小的可重复准备脚本。用例文字可以描述所需数据，执行时只调用可信项目清单明确登记的脚本，使用测试环境。

给端到端清单登记 `dataPreparations`，执行项通过 `dataPreparation` 引用。准备脚本建立状态，校验脚本从被测入口、应用状态或实际服务读回观测值，Runner 将观测值与登记的预期比较。会变更状态的用例另行保证隔离或重置。已有 CI 准备入口继续负责安装测试工具、部署构建和启动环境。运行 `open-vibecoding test-report e2e` 时先准备再校验，成功后进入实际用例。

准备或校验失败时，保留对应日志和可用观测值，将受影响用例记为未运行。成功的初始状态核对与后续业务断言各自记录。只交付用例清单时，仍使用 `render --kind cases`。

## 用例示例

**PHOTO-LIMIT-RETURN · 端到端**

- **初始数据**　相册有照片 P01–P09，搜索入口可找到 P10。开始时未选图。
- **操作步骤**　在相册选 P01–P09，转到搜索入口点 P10，再点完成回到发起页。
- **预期结果**　第 10 张被拦截，原名单保持，发起页收到 P01–P09。
- **关键断言**　尝试加入 P10 后出现上限反馈且 P10 未选中。按照片 ID 比较已选名单与初始名单，两者一致。回到发起页后，读取实际收到的名单并比较同一组 ID。
