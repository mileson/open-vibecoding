# 产品诊断

这是一种场景 Skill。用户直接说问题即可；不要让用户先选择五层、命令或完整流程。现有 `open-vibecoding-requirement-intake` 的 L0/L1/L2 用于判断开发工作怎么推进，产品诊断应先判断问题和证据。

## 诊断顺序

1. 写清用户要完成的任务、受影响的人、观察到的症状、时间与来源。把事实、用户解释和 Agent 推断分开。
2. 判断当前问题偏向完成任务、寻找或理解信息，还是两者都有；同一产品可以同时有两侧。
3. 从症状提出跨层候选原因。五层是判断视角，不是互斥标签或五道顺序关卡：
   - 战略：用户需求、产品目标和成功信号是否成立。
   - 范围：功能与内容是否恰当，有无缺失、冗余或不可维护的内容。
   - 结构：交互流程、概念模型、信息架构和错误恢复是否符合用户任务。
   - 框架：界面、导航、信息呈现与控件布局是否帮助用户识别和行动。
   - 表现：感知层级、视觉、声音、触觉与反馈是否支持前面四层。
4. 为每个候选原因列出已有证据、反例和关键未知。优先选择能区分竞争假设的最小研究动作：访谈现有做法、观察真实任务、检查内容、分析行为数据或做原型测试。
5. 只把有依据的判断写成结论。证据不足时标记 `unknown`，给出下一次观察或验证方式；不要把低使用率直接归因为按钮颜色，也不要把口头偏好当实际行为。
6. 明确改动目标后，再交给 `$open-vibecoding-requirement-intake` 判断 L0/L1/L2；若主要问题在交互结构、框架或表现层，交给 `$open-vibecoding-interaction-design` 继续。

## 最小交接

输出用户任务、症状、主要与次要候选层次、事实来源、假设、反例、未知项、建议验证、当前判断及成功信号。下一步产物必须能直接成为产品、交互、研发或测试能力的输入。不要因为需要深度调研，就把所有五层强制走一遍。

## 来源与边界

五层借鉴 Jesse James Garrett《The Elements of User Experience》的战略、范围、结构、框架、表现模型。Steve Krug《Don't Make Me Think, Revisited》用于检查用户是否看懂选择、能否确认方向，以及通过实际任务观察而非争论喜好发现问题。这些是诊断方法，不替代当前项目证据。
