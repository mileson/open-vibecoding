# 界面交互 Review

这是测试域的独立审查子能力。按用户希望检查实际体验的意图选用；方案尚未实现时，交给 `$open-vibecoding-interaction-design`。本场景让 reviewer 发现并说明问题，用户要求同时修复时由 `$open-vibecoding-ui-review-and-repair` 组合调度。

复用 `$open-vibecoding-test-strategy` 的“真实用户操作优先验证”：按测试用户的真实目标检查最终业务结果，而不只是遍历按钮。普通验收可以由当前 Agent 完成；本能力只在需要独立 reviewer 时组合。若改用 Playwright 等自动化，应按普通验收说明方式和范围，不宣称已完成本能力要求的 Computer Use Review。

## 独立 reviewer

主 Agent 单独 spawn 一个 reviewer，使用宿主现有的 subagent 能力。传入目标用户、要完成的任务、目标应用或 URL、范围、测试数据与账号角色、当前版本和明确的产品约束。尽量给最小上下文，不把实现者的设计辩解、预期问题清单或“应该没问题”的判断灌给初次审查者。

角色是有经验的产品经理：关注用户能否找到入口、理解选择、完成任务、得到反馈和从错误中恢复。角色称谓不构成正确性的证据，发现必须能指向实际行为。Reviewer 不修改产品代码、不发起修复；允许保存必要截图或操作证据。

## 亲自操作界面

- 开始前核实 reviewer 自己是否可用 Computer Use，以及目标窗口、页面、运行版本和测试环境。复用一个任务专用浏览器会话；同一时刻只有一个 Agent 控制界面。主 Agent 有工具不代表子 Agent 也有。
- 按实际页面建立轻量覆盖清单：入口、按钮、链接、菜单、表单、弹层、导航以及操作后出现的新控件。结合用户任务逐个点击、输入和返回，观察操作前后结果；仅看源码、DOM、截图或运行脚本不算亲自完成交互检查。
- 优先跑完整用户路径，再检查相关的空状态、加载、校验、失败反馈、关闭或取消、返回与重复操作。按范围遍历状态中可达的交互；“所有按钮都检查了”必须有相应覆盖依据。
- 成功提示后继续检查用户实际得到的内容：保存后重开、使用已开通权益、打开导出文件等。记录沙箱、回放或模拟环节；界面表现正常不能单独证明付款、后台数据或媒体质量真实正确。
- 真实发送、付费、删除业务数据等动作使用已授权测试数据与环境；无法在当前范围安全触发的操作标为未验证。不要为达到覆盖数字操作真实用户数据。
- 先说明预期行为的依据，再报告实际差异。产品故障、可用性阻碍、视觉偏差和主观改进建议分别说明；视觉喜好不能直接判定为 bug。
- Computer Use 或目标环境不可用时，返回具体缺口和已检查范围。其他检查可以补充，但不得宣称完成了浏览器交互 Review。

## 可供修复者使用的问题

每个可行动问题给出：稳定的问题标识、页面与状态、用户影响、复现步骤、预期及依据、实际结果、对应版本、截图或观察证据、严重程度和确定程度。只在确实需要时保存证据文件；问题交接可直接留在对话中，不创建 PRD/change/tasks。

收口同时说明已覆盖的路径与控件、跳过项及原因、尚未验证的状态。没有发现问题只能说明本次覆盖范围内未发现问题。后续复查时保留问题标识，并区分“仍可复现 / 已修复且复测通过 / 未能复测 / 仅建议”。
