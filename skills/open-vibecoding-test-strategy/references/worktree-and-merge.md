# 工作区选择与合并冲突

## 选择工作区

按用例核对实际要验证的提交、构建和路径。查看当前目录的分支、HEAD、未提交改动及占用情况，确认是否有其他人或 Agent 同时修改待测代码。只在实际源码或构建与待测版本一致时，把结果记到该提交。若有本任务刻意保留的未提交改动，范围应明确并记入实际待测状态。

| 场景 | 决策 |
| --- | --- |
| 相同提交，仅执行现有测试 | 代码目录稳定时复用。测试重置数据、端口、报告、trace 和构建输出按任务隔离，确认测试本身不会写坏共用工作区。 |
| 并行修改代码或分别验证不同提交 | 优先复用归属和版本吻合的任务 worktree。只有明确获准才新建。缺少授权或合适的目录时，继续执行安全的检查，列明未覆盖的变更或提交。 |
| 共享且无法隔离的运行资源 | 串行使用同一模拟器、账号、数据或端口。仅在运行资源也独立时并行。会改变共享服务状态的 Playwright 测试，具备条件时可给每个并行 worker 分配独立测试账号。 |

任务 worktree 的 `--root` 和 `--data` 指向同一工作区，`--out` 使用任务独立路径。沿用 `test-report e2e --require-worktree` 校验路径。这个参数检查 linked worktree 和清单位于同一目录，待测提交和资源归属由 Agent 另行核实。 [Git worktree](https://git-scm.com/docs/git-worktree) · [Playwright 并行测试账号](https://playwright.dev/docs/auth#moderate-one-account-per-parallel-worker)

### 工作区 Good Case / Bad Case

| 情形 | Good Case | Bad Case |
| --- | --- | --- |
| 同一提交，Web 和 iOS 只执行已登记的选图回归 | 核对两个构建和代码都来自同一提交，复用稳定的代码目录，分别准备数据并保存报告。 | 为每条验收用例都建 worktree，重复准备相同源码和资源。 |
| 两个人或 Agent 并行修不同缺陷 | 核对任务和版本后，各自在已有且归属明确的任务 worktree 修改和验证。确需新建时沿用已获授权。 | 在同一目录交叉编辑，一个任务的构建混入另一个任务还在改的文件，仍把结果归到各自提交。 |
| 两个任务都需要同一台 iOS 模拟器 | 复用这台已确认归属的模拟器，按任务串行装包、准备数据和验收，分开记录证据。 | 认为用了两个 worktree 就能并行操作同一模拟器，导致启动版本、数据或截图被覆盖。 |

## 分级处理合并冲突

先找用户确认的需求、验收条件和已有项目契约。再读双方 PR 的意图、共同祖先和各自差异，确认每一处改动要保留的行为。用已有测试和实际运行验证结论，断言不足时补能同时覆盖双方改动的用例。三方合并时可用 `git ls-files -u` 及对应文件在索引中的版本查找冲突前后的依据。 [Git 三方合并与冲突处理](https://git-scm.com/docs/git-merge#_how_to_resolve_conflicts)

| 层级 | Agent 何时可以自行处理 | 合并后核对 |
| --- | --- | --- |
| 机械冲突 | 两边行为一致。按项目规则整理格式、合并必要导入，按合并后的源文件和项目既有工具重新生成产物。 | 核对双方符号、配置或源文件改动仍在。按影响跑格式检查或构建。 |
| 代码结构冲突 | 重命名、移动或调用迁移的映射明确，双方契约仍成立。做最小迁移，顺着调用链核对已有调用方。 | 构建或类型检查，再跑受影响的单测、接口或集成测试。 |
| 业务逻辑兼容 | 已确认的规则和两边有效行为可同时成立，能给出分别及组合后的验证证据。 | 运行双方回归，补组合路径断言和必要的关键端到端验证。 |
| 业务规则互斥或高影响依据不足 | 规则、权限、迁移或数据后果存在待定决策时，由负责人定夺。继续处理能独立解决的冲突。 | 反馈争议规则、双方依据、可选方案、各自影响和待验证项。等决策明确后按最终规则复测。 |

只在自己有权修改的任务工作区做最小处理。禁止默认整块采用 `ours` 或 `theirs`、按提交时间选业务规则、放宽断言换取通过、跳过评审或门禁。即使 `rerere` 找到历史解法，也要读本轮差异并复测，确认旧解法仍满足当前需求。 [Git rerere](https://git-scm.com/docs/git-rerere)

### 合并冲突 Good Case / Bad Case

| 情形 | Good Case | Bad Case |
| --- | --- | --- |
| 两边改了同一段导入或生成文件 | 合并仍被调用的导入，从包含双方修改的源文件重新生成产物，再跑格式检查和构建。 | 整个文件选一边，构建恰好通过，却丢掉另一边的生成配置。 |
| 一边重命名接口，另一边增加了调用 | 从共同祖先及双方差异确认这是同一个接口，把新增调用迁到新接口，并验证旧有和新增调用的行为。 | 盲选一边，保住了重命名却删掉新增调用，或保留已经失效的旧调用。 |
| 一边重构搜索入口，另一边修复第 10 张图的拦截 | 已确认上限是 9 张。保留新入口并接上拦截，从相册选满后切去搜索点 P10。验证第 10 张被拦、原 9 个 ID 保持、点完成后发起页收到同一名单。 | 只验证总数等于 9 就宣称合并完成，漏掉 P10 替换 P01。 |
| 同一入口的两个 PR 分别要求最多 9 张和 12 张 | 把两条验收原文、受影响的入口和边界、各方案对已有用例的影响交负责人。先处理独立冲突，拿到决定后按确认的上限复验。 | 根据更新时间或哪一套测试先绿选一个上限，再改写断言让另一边也通过。 |

## 复验合并候选与收尾

获准更新 PR 后，验证最终候选的实际提交与预期一致，再按仓库的评审和必过检查合并。启用 GitHub 合并队列时，以队列生成的合并候选为准，满足仓库要求后由队列自动合并。候选因目标分支或排队变动而更新时，使用更新后的检查结果。 [GitHub 合并队列](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)

按已授权的流程清理前，核对对应 PR 已合入、最终改动进入目标分支、本地任务工作区干净、归属明确、无人占用。普通合并可看提交包含关系，squash 或 rebase 合并要结合已合并的 PR 和目标分支结果核对，尤其要确认没有遗漏其后的新提交。按宿主或仓库规则归档或移除任务 worktree，再清理确认已合入的临时分支。遇到失败、未合入改动、状态不明或清理受阻时，保留工作区、差异和报告。
