# 真实用户操作优先验证

属于 Open VibeCoding 测试模块，统一使用新版 Skill 入口。Agent 自主理解任务、安排测试；本指南提醒如何证明用户的事情确实办成，不接管思考方式，不用固定关键词或正则匹配场景。

## 先问用户最终要得到什么

涉及用户可操作的功能时，优先在运行中的产品里，以测试用户身份，从真实入口完成本次改动影响的业务流程，并检查最终结果。工具代替人点击、输入不是伪造业务结果；把接口或结果预设为成功则是模拟，不能混称真实链路验证。

以本次任务为边界，不要求每次把整个产品跑一遍。纯文档、内部局部逻辑或无界面的工具不为形式强开浏览器，选择对应的实际消费入口和结果验证。轻量视觉调整检查相关页面状态，不升级为全产品回归。

## 验收关注的优先级

1. **用户能否办成整件事**：从入口完成关键路径，检查保存后的内容、实际权益、导出文件或其他最终结果；按钮可点、成功提示、构建成功和单张截图不能替代结果验证。
2. **环节是否接得上**：核对上一步的真实结果是否被下一步正确使用，尤其关注权限、支付、跨服务、保存再打开以及恢复任务。
3. **典型案例是否仍然正确**：用脱敏的历史故障输入、代表性真实样本和已确认结果复测。黄金样本可用于完整流程或环节验证，不是每次必加的独立层；不得仅为了通过测试更新基准。AI/媒体结果按关键内容、允许差异或质量标准判断，不机械要求逐字或逐像素相同。
4. **关键局部规则是否准确**：金额、权限、额度、重复执行、边界计算等适合用快速小测试补充。不为每个函数凑测试，不按数量、覆盖率数字或固定比例判断业务已经可用，也不因此删除已有有效测试。

这是证据价值的考虑顺序，不是固定执行顺序。开发中可以先跑低成本局部检查；它通过后仍不能代替本次需要的真实用户路径。

代码变更按 `$open-vibecoding-code-quality` 的三个研发阶段推进，优先先写目标行为的失败测试，再实现与整理。测试先行规定开发时机，真实用户结果规定验收标准；两者同时成立。关键逻辑的测试是否真正有效，可独立组合 `$open-vibecoding-test-strength-review` 使用 Mutator，仍需区分存活、未覆盖、等价变异、超时与环境失败，不凭变异总分代替业务验收。

## 按当前可用能力选择工具

涉及有限资源消费或使用权益的功能，按需组合 `$open-vibecoding-resource-entitlement-design`，从资源取得到消费、失败恢复和运营读回核对业务结果；仅模拟余额不能证明真实资源链路成立。

- Codex、Claude 等客户端实际提供可安全使用的 Computer Use 时，优先通过它亲自操作目标浏览器或应用。先确认工具可调用、窗口归属、运行版本和账号角色；不能仅凭客户端名称推断能力存在。
- 网页的稳定重复回归可使用 Playwright 等现有工具；Computer Use 不可用或无法安全控制目标时，也可用实际可用的网页自动化完成验证。说明采用的方式，不把脚本执行冒充 Computer Use 操作。
- 宿主规则允许且本次选择用 Playwright CLI 探索网页时，先在目标项目运行 `open-vibecoding tools ensure playwright-cli`。从结果的 `installation.command` 与 `installation.args` 取得已验证的命令，对目标项目追加业务参数。缺失时由 Open VibeCoding 安装到管理缓存；网络或安装失败时保留原因。常规 Playwright Test 或 Maestro 回归继续使用项目的测试执行器。
- 原生移动端的可重复路径可使用 Maestro。执行前运行 `open-vibecoding tools ensure maestro`，iOS 执行可传 `--device <iOS-UDID>` 核对指定模拟器；CLI 缺失时按需安装，Java 或设备未就绪时记录具体原因。登记应用构建、目标设备和系统版本。明确报告运行在模拟器、真机还是样例应用；各自按实际覆盖范围给结论。
- 涉及原生应用、系统权限、后台切换或平台差异时，在对应平台验证。网页、模拟响应或模拟器不能代替它们未覆盖的真机行为。微信小程序按宿主要求使用实际可用的专用验证能力。
- 不为普通验收强制新增依赖、启动浏览器或派发 subagent。需要独立产品视角时组合 `$open-vibecoding-ui-interaction-review`；用户要求修复再组合 `$open-vibecoding-ui-review-and-repair`。Reviewer 自身也要核实工具是否可用，同一界面同一时刻只由一个 Agent 控制。

## 真实场景不等于默认操作生产环境

优先复用可控的测试环境、测试账号和有代表性的数据，覆盖本次相关的正常路径、必要失败与恢复场景。生产验证须有相应授权和明确范围；真实扣费、消息发送、删除业务数据等不能因“要测完整”而自动获准。测试账号也不代表不会影响真实系统。

外部服务不可控、成本高或故障难以安全制造时，可使用沙箱、回放或模拟响应补充测试；明确被替代的环节及结论边界。支付沙箱成功不等于真实生产扣款成功，模拟会员生效不等于实际购买链路已验证。关键真实环节缺失时，报告未验证，不通过放宽断言或伪造结果宣称完成。

复用当前任务环境，重资源默认串行；失败先读现有日志，不反复重启、堆开模拟器或清全部缓存。结束只清理本任务创建且不再需要的资源。

## 把功能验收变成可重复的断言

从同一份需求写下初始数据、用户动作、动作后的状态和接收方真正拿到的结果。优先对可确定的数据、状态与副作用写明确断言。评测 AI 功能时读取实际返回、实际界面或结果数据，语义质量等无法可靠用确定性条件判断的部分才单列评分准则与证据。

例如「最多选 9 张」：用固定的照片 ID 选满 9 张，从搜索入口点第 10 张，检查拦截且原 9 个 ID 不变。点完成后，在发起页核对收到的仍是同一份名单。可先用一个已知缺陷验证断言能否检出静默替换，再在修复版本复测。保留数量检查和身份检查的真实结果，比较两套断言的覆盖情况。

需要重复运行并交付报告时，使用 `open-vibecoding test-report e2e`，从 Playwright JSON 或 Maestro JUnit 读取实际结果。对每条功能验收项保留期望、观测值和失败截图或 trace，区分断言失败、环境或执行错误、未运行和重跑通过。用 `open-vibecoding test-report e2e --help` 查看入口，项目接入说明见发行包的 `docs/test-report.md`。

CI 的 PR 检查优先跑受影响的关键路径，夜间与发布前跑完整登记范围。必过项使用正确的业务基线，已知缺陷对照单独运行。AI 可辅助分析失败证据，合并判断采用项目明确的验收断言和运行状态。

## 启动验收时选择工作区

从用例关联的待测提交查起，主动核对是否有人并行改代码、工作区归属和未提交改动，以及账号、数据、端口、模拟器和产物是否能隔离。同一提交只执行现有测试，且目录稳定、运行互不干扰时，复用工作区并隔离测试数据和输出。并行改动或分开验证不同提交时，优先复用归属和版本吻合的任务 worktree。只有已有明确授权才新建。缺少授权或合适工作区时，先完成可安全验证的部分，说明未验证的提交或路径。共享且无法隔离的资源串行。

在任务 worktree 运行时，将 `--root` 和 `--data` 指向同一工作区，使用 `test-report e2e --require-worktree` 校验，并指定独立的 `--out`。选择或复用工作区前，按需要读 [工作区决策和正反例](references/worktree-and-merge.md#选择工作区)。

## 分级处理合并冲突

先以已确认的需求、验收条件和项目契约为准，再借双方 PR 意图、共同祖先和差异还原改动。机械冲突、代码结构冲突和可证明兼容的业务冲突，可在自己有权修改的任务工作区做最小合并，并按影响复验双方行为。业务规则互斥，或权限、数据迁移等高影响变更依据不足时，提交争议和选项影响给负责人，先处理其余独立冲突。详细分级、验证和正反例见 [合并冲突处理](references/worktree-and-merge.md#分级处理合并冲突)。

获准更新 PR 后，在最终合并候选上复验，按仓库评审和门禁规则合并。已授权清理时，先确认对应改动已合入，核对工作区归属、干净状态和占用情况，再按宿主流程收尾。失败或仍有争议时保留工作区、差异与验证证据。

## 如何收口

用业务语言说明：在哪个环境和版本、以什么角色、实际做了什么、观察到什么结果、哪些环节用了模拟、哪些仍未验证。只保留能支持结论的必要证据，区分通过、失败、未运行与无法验证；未知不等于失败或通过。

界面视觉审查必须落实 `$open-vibecoding-visual-evidence-delivery`：最终回复嵌入本轮实际截图；有确认参考时展示参考与实际结果，无参考时展示最终实际界面。仅保存图片、给路径或文字说通过不算交付；无法取图时标记视觉未验证。媒体从最终产物复测；截图与亲自点击均不能替代后台数据或成片质量验证。不要求创建 tasks、evidence-plan、Markdown/HTML 测试报告；只有用户或复杂审查确实需要时才制作长期材料。

需要把这些原则转成具体操作时读 [业务场景示例](references/user-journey-examples.md)。

## 需要交付单元测试报告时

先确认被测行为、范围和预期，再按项目已有入口生成、运行和记录。分别记录四层的实际证据。单元测试验证选图上限一类的业务规则，组件测试验证交互反馈，接口／集成测试验证服务契约，真实用户路径从产品入口检查最终结果。

执行后按用例标识导入框架原始结果，保留未匹配的结果和复测记录。用例没运行时保留待测试，环境阻塞、跳过、取消、不支持和未知各自记录。结论只覆盖本次有证据的范围。使用生成和运行 Skill 分别处理已有授权范围内的动作。
