# 重构与质量改善

先明确要降低的具体维护成本和必须保持的行为合同。读取相关调用方与测试，确定可安全移动的边界；用户现有未提交改动必须保留。

- 用小而可验证的步骤调整职责、依赖或命名；不要为了达到抽象层次而引入新的状态机、配置或文档流程。
- 若行为确需改变，把该部分显式当功能改动处理，不以“重构”掩盖。
- 前后运行同一组关键测试或等价行为验证，并检查兼容入口。`dev-check` 的大文件提醒是线索，不是自动拆分指令。
- 报告结构改善与行为证据；只有现有活文档失真时才同步说明。
- 伴随性能改善或故障处理时，用 `$open-vibecoding-diagnostic-readiness` 检查诊断盲区与可比较的耗时证据；纯结构整理不机械新增日志，已有有效诊断点不因重构而丢失。
