# 生成单元测试

1. 从用户目标、已确认需求、相邻用例或历史故障确定可观察的预期。记录断言依据。若当前实现和已确认行为冲突，保留差异，用测试复现。预期不明确时，列出待确认行为，继续覆盖已明确的部分。
2. 确认实际模块和测试入口。检查项目规则、脚本、CI、测试目标和相邻测试。复用现有框架、目录、fixture 和 mock。缺少可执行入口时说明缺口。只有任务包含搭建测试基础设施时才新增依赖或配置。
3. 选择会影响结果的正常流程、边界、失败恢复和已知回归。把时间、随机、外部 I/O 等不可控依赖隔离在明确的边界。用状态、输出或行为断言验证结果。异步状态用可控信号和时钟，避免固定睡眠。
4. 把用例放进仓库已有的发现范围。交付测试文件、覆盖的行为、预期依据、执行入口和未覆盖范围。只要求生成时，只修改测试，不执行测试或修改业务代码。需要执行时组合 `$open-vibecoding-unit-test-run-and-repair`。

## 按模块选择用例

| 模块 | 单元测试重点 | 另行验证 |
|---|---|---|
| 官网、内容站 | 路由和内容索引、版本和下载项选择、本地化规则 | 页面导航、实际下载 |
| Web 后台、数据产品 | 表单规则、筛选去重、状态切换、聚合和失败恢复 | 浏览器操作、服务端持久化 |
| iOS | ViewModel、状态迁移、几何与格式转换。沿用目标目录的 XCTest 或 Swift Testing | 真机硬件、系统权限、界面操作 |
| 服务端、Python | 业务计算、数据转换、错误映射、重试和幂等规则 | HTTP、数据库和外部服务契约 |
| 扩展、桌面、CLI | 数据解析、消息转换、队列状态、参数和退出码 | 扩展宿主、进程通信和完整业务流程 |

同一项目可有多类模块。根据本次行为和风险选择，用户路径和其他验证层按 `$open-vibecoding-test-strategy` 补齐。

## 从用例交接到执行

用一句话写明被测行为和范围，再为每条用例保留输入、可观察的预期和断言。给业务用例一个稳定 `id`，实现后在 `testIds` 登记对应框架给出的标识。参数化用例要保留框架输出的参数标识。当前只要求生成时，可交付待测试清单，执行和修复仍按各自授权。

- iOS 先检查 scheme、测试计划、测试目标和同目录的 XCTest / Swift Testing 用法。
- Web 先检查现有 Vitest / Jest 脚本、环境配置和文件发现规则。纯函数与状态规则放在单元层，组件渲染和输入交互放在组件层。
- Python / FastAPI 先检查 pytest 配置和已有 fixture。纯业务规则放在单元层，调用应用路由、数据库或外部服务合同的测试归接口／集成层。
- 正常路径检查业务结果，边界覆盖阈值前后，恢复检查失败后能否继续，回归保留原故障的输入和断言。真实入口、系统权限和最终保存结果按测试策略另行验收。

## 复杂改动的分组计划

沿模块和业务流程列出功能组，将每条业务规则关联到稳定的规则 ID。明确属于单元层的行为；真实页面、网络和存储的联动留给相应测试层。即使暂时没有对应测试，也保留规则，以便报告显示「缺用例」。

每个用例独立写清准备数据、执行动作、预期结果及实际断言。准备数据包括初始状态、最小输入和需要替代的外部依赖。为关键分支安排边界值、状态恢复和已知故障用例。断言同时检查必要的返回值、不变量和状态变化。比如选满后拦截第 10 张，除了总数还要验证原名单不变。

业务步骤有先后时，为测试分别构造所需的初始状态。有真实执行依赖才填 `dependsOn`。资源可隔离的组可以并行；共用不可隔离的模拟器、端口或夹具时填相同的独占资源名。将功能组、规则、用例与项目原生运行目标交给运行 Skill；用 `open-vibecoding test-report plan --data cases.json` 校验。简单改动可直接沿用现有测试方式。
