# 生成单元测试

1. 从用户目标、已确认需求、相邻用例或历史故障确定可观察的预期。记录断言依据。若当前实现和已确认行为冲突，保留差异，用测试复现。预期不明确时，列出待确认行为，继续覆盖已明确的部分。
2. 确认实际模块和测试入口。检查项目规则、脚本、CI、测试目标和相邻测试。复用现有框架、目录、fixture 和 mock。缺少可执行入口时说明缺口。只有任务包含搭建测试基础设施时才新增依赖或配置。
3. 选择会影响结果的正常流程、边界、失败恢复和已知回归。把时间、随机、外部 I/O 等不可控依赖隔离在明确的边界。用状态、输出或行为断言验证结果。异步状态用可控信号和时钟，避免固定睡眠。
4. 把用例放进仓库已有的发现范围。交付测试文件、覆盖的行为、预期依据、执行入口和未覆盖范围。只要求生成时，只修改测试，不执行测试或修改业务代码。需要执行时组合 `$open-vibecoding-unit-test-run-and-repair`。

## 按模块选择用例

| 模块 | 单元测试重点 | 另行验证 |
|---|---|---|
| 官网、内容站 | 路由和内容索引、版本和下载项选择、本地化规则 | 页面导航、实际下载 |
| Web 后台、数据产品 | 表单规则、筛选去重、状态切换、聚合和失败恢复 | 浏览器操作、服务端持久化 |
| iOS | ViewModel、状态迁移、几何与格式转换。沿用目标目录的 XCTest 或 Swift Testing | 真机硬件、系统权限、界面操作 |
| 服务端、Python | 业务计算、数据转换、错误映射、重试和幂等规则 | HTTP、数据库和外部服务契约 |
| 扩展、桌面、CLI | 数据解析、消息转换、队列状态、参数和退出码 | 扩展宿主、进程通信和完整业务流程 |

同一项目可有多类模块。根据本次行为和风险选择，用户路径和其他验证层按 `$open-vibecoding-test-strategy` 补齐。
