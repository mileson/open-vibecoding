# 产品使用数据分析

从用户要作出的业务判断出发，例如“注册后为什么很少有人完成第一次使用”，而不是先列所有指标。按场景理解任务，不用固定关键词分流。

## 分析提醒

- 优先复用当前产品已有的数据源、报表或用户提供的导出数据。需要查询工具或接入帮助时，按需使用 `$open-vibecoding-tool-selection`；不要求安装某个厂商工具或外部 Skill。
- 查询前从项目事实确认目标产品、环境、时间范围、时区和比较对象；目标不明确且会影响结果时再询问。不因账号有访问权限就遍历全部产品。
- 先核实指标含义与口径：人数还是次数、分母是什么、哪些用户被纳入、事件何时开始采集。比较转化与留存时保持事件定义、用户群、观察窗口一致；未成熟的留存窗口不能当完整结果。
- 先看汇总，再按有助于解释问题的版本、渠道或用户群深入，避免拉取无关个人明细。区分真实变化与采集缺失、重复事件、上报延迟或口径变化；缺失值不当作零。
- 将观察到的事实与原因假设分开。数据相关不等于因果，小样本和未知口径要限制结论，必要时建议最小验证，而不是凭一条曲线要求改产品。

## 交付与边界

用业务语言说明哪里发生变化、影响多少用户、证据和口径是什么、还有什么不能确定，以及下一步值得验证什么。工具能获取时附查询或报表来源；拿不到人数、采集覆盖或更新时间时标明未知，不猜测。

分析默认只读，不顺手改埋点、安装 SDK、修改指标或发布产品。没有可用数据时输出数据缺口和可选接入建议，不编造分析结果；已授权的数据文件分析不因缺少在线工具而阻断。

## 按需交付 HTML

1. 核对数据来源、事件定义、分母、去重方式、时区、观察窗口和可比较范围。保留可追溯的查询、报表或导出记录，只在报告中呈现任务需要的汇总。某个分析环节只是估算或待核实时，在正文标明证据边界。
2. 先写业务总结，再选关键指标。总结写清观察、影响和未知项。分析结果只支持相关性时，用假设表达原因。需要提醒下一步核对时，在 `summary` 末尾写一句，省略独立的下一步验证区。
3. 按问题挑选所需卡片。流程到达和流失用 `funnel`，按日期的变化用 `trend`，版本、渠道或平台差异用 `comparison`，同一入组日期的后续留存用 `cohort`。可组合多张卡片，也可只交付总结和指标。趋势缺失值填 `null`，留存用同一时区的最后完整数据日判断窗口，未成熟单元格留空。
4. 将业务总结写入 `summary`，在 `scope`、`context` 或卡片 `note` 标明适用口径。已核实报告起止日期时填写 `dateRange.start/end`，页首右侧只显示日期。趋势提供 `dates`、`series[].values` 和 `unit`，数值和日期刻度由模板生成。

用 `open-vibecoding funnel-report render --data report.json --out report.html` 直接采用内置模板，默认样式随命令生成。查看 `funnel-report render --help`，可从仓库的 `docs/funnel-report.md` 复制 JSON 示例。读回报告，按总结、关键指标、必要明细的顺序核对证据和数据缺口。

默认版式中，纵向漏斗步骤表的到达人数用模板蓝，流失注释用中性色。趋势保留横向网格，左侧只有刻度值。已知点之间的缺失区间用虚线，缺失单元格显示「—」。只有实线下方带同色半透明渐变。前五条趋势线按输入顺序使用粉红、蓝、炭黑、紫、金黄，平台名称只作为图例标签。

不要求生成 PRD、change、tasks 或固定分析报告文件。数据指向运行故障时可按需交接给 `$open-vibecoding-production-anomaly-analysis`；需要修复或持续监控时另按用户授权推进。
