# 精简实现与工程质量

研发内部使用，供功能实现、修复和重构自动组合。代码变更遵循下列三个阶段；小改动可以在一个短循环里完成，不要求建立阶段文件、PRD、change、tasks 或逐步操作日志。产品调研、方案讨论与只读诊断仍保持原有范围。

## 第一阶段：先把功能做对

先确定用户能观察到的结果、数据结构和约束。优先写能够暴露目标问题的失败测试，亲眼确认它因预期原因失败，再做最小实现让它通过。新功能可先写预期行为测试，修复可先写复现测试；重构先固定现有行为，不制造虚假的失败。确实无法写可靠自动测试时，说明缺口并用可重复的实际操作或样本验证，不为了测试先行编造断言。

明确状态、外部输入边界、重复执行与失败恢复；优先减少已有复杂度。新需求与原设计不合时从业务目标重新判断边界，分块落地，避免层层加补丁。连续两次修复基于同一个假设却仍失败时，重新检查假设和状态归属，再继续。详细设计提醒见 [实现原则](references/principles.md)。

复杂、重复或容易出错的操作，先完成一个可核验的小样本，再把方法做成项目可复用工具。已有工具足够则复用；脚本与使用方法放到项目已有工具目录或项目级 Skill，验证输入、输出、失败恢复和重复执行。创建或修改 Skill 遵循宿主已有授权规则，不把普通编码授权扩大成全局规范修改。未来跨项目提炼时移除个人路径、凭证和业务绑定。

## 第二阶段：再把代码整理好

检查根因、重复规则、职责与行为测试。每次小幅整理后复测，保持已经正确的行为。按变更范围、语言与工具可用性组合三个独立能力：

- `$open-vibecoding-code-complexity-review`：调用 Crapper，检查复杂且缺少测试的函数，默认改善目标为 CRAP 小于 10。
- `$open-vibecoding-code-duplication-review`：调用 Dryer，显式筛出相似度大于等于 0.8 的重复候选，判断是否应共享同一业务规则。
- `$open-vibecoding-test-strength-review`：调用 Mutator，检查故意改变逻辑后测试能否发现错误。

三个工具串行执行，优先覆盖本次改变的代码；不按关键词路由，不把每次任务升级为全仓扫描。数字用于定位和改善，不能靠拆空函数、无意义抽象、跳过难测代码或修改正确预期来过关。工具缺失、语言不支持、覆盖率无效时明确未完成的检查，继续其他有效验证；不伪装成工具已通过。工具安装与调用见 [工具接入](references/quality-tools.md)。

结合 `$open-vibecoding-test-strategy` 从实际用户入口检查最终业务结果。先写失败测试是开发顺序，业务结果优先是验收标准，两者同时成立。涉及视觉仍交付本轮真实截图。

## 第三阶段：完成工程收尾

- 主线程保留目标、关键决策、改动与验证摘要、未决风险及必要路径。长日志按问题检索或保存到现有临时位置，不反复全文加载；不为减小上下文强制派生 Agent，确有独立工作且宿主允许时才委派并收回证据摘要。
- 检查本次生成的可复用工具是否可被后续任务找到和调用；普通过程不要求另写复盘或每一步的操作记录。
- 按项目约定整理小而完整的提交，说明目的、改动与验证；提交和推送遵循已有授权、仓库身份与主分支规则。已授权发布时完成主分支整合、推送与读回，不以质量检查为由扩大公开范围或自动发布。
- 默认复用当前分支；需要且获准使用 worktree 时，按解决的问题或新增功能命名，例如 `【修复】断网后登录恢复`。工具不支持中文时用同义英文目录名，保留可识别的任务名称。
- 清理前核对 worktree、分支和临时资源归属、活跃引用与合并状态。仅清理本任务有权限处理且已不需要的对象；未提交、未合并或其他任务使用的内容保留。已授权发布须完成主分支收尾后再清理。

交付简述业务结果、实际检查、仍需处理的质量问题和工程收尾状态。原方法的全部主题与本项目的取舍映射见 [实现原则](references/principles.md)。
