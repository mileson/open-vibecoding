# 收款通知验收案例

按本项目实际改动选择必要验证，优先复用已有测试环境与数据；这里不要求每次新建测试平台或后台。

| 场景 | 应核对的结果 |
| --- | --- |
| 可信收款与必要业务提交完成 | 对应事件可进入发送队列，卡片内容与支付事实一致 |
| 创建订单、客户端成功提示、验签失败或币种/金额/商户不符 | 不发送正式收款卡 |
| 权益提交失败或事务回滚 | 不产生声称已完成的收款与交付通知；按项目规则恢复 |
| 重复回调及并发处理同一事件 | 项目持久化去重生效，不重复创建待发送事件；重试使用同一业务身份 |
| 同一订阅的两笔续费 | 两笔独立交易各自通知，不因订阅 ID 相同被合并 |
| 通道拒绝、限流、网络失败或超时 | 支付结果不回滚；区分永久错误、可重试与结果未知，记录恢复依据，不无界重试 |
| 发送成功但回执保存前中断 | 从项目事件与通道可用证据恢复，不直接生成新身份重复发送；缺少核对能力明确说明 |
| 不同币种、金额精度、语言与时区 | 数值和时间源保持真实，展示按项目配置，不混用货币符号或通知发送时间 |
| 商品名包含引号、换行、Markdown 符号或模板形状字符 | JSON 保持合法，文字保持原意，变量值不被再次当模板解析或新增链接 |
| 订单号与两个跳转入口 | 订单号完整可读，单笔详情与产品订单列表分别正确，链接不含凭证并继续鉴权 |
| Logo 与主题 | 发送应用能访问 Logo；浅色和深色的金额、正文与按钮可读，检查手机及桌面实际显示 |
| 测试试发 | 使用明确授权的测试目标，消息和摘要能与正式收款区分；复用相同渲染逻辑，生产载荷不带测试标识 |
| 更新 Open VibeCoding | 托管参考模板可以更新；业务项目已复制、已定制的模板和发送配置保持原样 |

静态 JSON 校验不证明飞书支持所有字段，也不证明已经送达。实际试发后回读消息内容，再检查飞书客户端的 Logo、布局和链接。没有实际发送授权时停在静态验证，交付写明剩余验证范围。支付系统的软件测试身份属于必要的测试语义，不将其混入生产卡片。
