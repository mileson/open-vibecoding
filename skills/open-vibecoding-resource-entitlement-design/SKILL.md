# 资源权益与运营配套

让功能不仅能运行，还能解释用户拥有什么、如何使用，以及运营如何处理例外。先读现有产品规则、实现、账户与管理入口，再选择本次相关的检查视角；它们不是必须依次执行的流程，不接管 Agent 规划。

## 按业务判断是否适用

如果一次操作会消耗有限资源、改变可用权益，或涉及资源发放与恢复，就检查下列相关方面。依据实际行为判断，不靠名称命中。普通不限量功能无需引入资源系统；订阅资格、消耗余额、供应商成本和请求限流分别建模，不因都叫“额度”就混为一谈。

## 需要想深一层的地方

- **资源怎么算**：一次点击、一次成功产出、一分钟或一份容量，哪一个才是计量单位？谁拥有和使用它？复用现有权益与账户边界；只有共享账户、跨设备等确实存在时才扩展考虑。
- **资源从哪来**：按实际业务考虑免费配额、购买、套餐分配、活动赠送或补偿；检查到期、重置、续期、不同资源桶的使用顺序。不是每种来源都必须实现，区分已确认规则与待确认选择。
- **什么时候扣、如何恢复**：按产品承诺确定直接扣减或预留后结算，以及失败、取消、部分完成、上游超时但结果未知时的处理。重试、重复回调和并发不能造成重复扣减或漏记；不要一律规定成功才收费，也不要把用户退回次数等同于供应商退费。未知状态需能查询、核对或补偿，不能盲目再次消费。
- **运营怎么处理**：判断本次是否需要策略调整、查询、补发、撤销或补偿。优先复用已有管理页、后台接口或受控 CLI，只实现最小必要配套；关注操作权限、发放原因、有效期、重复提交防护、变更记录，以及新策略对已有用户和进行中任务何时生效。
- **用户是否看得懂**：让用户理解已用、剩余、待结算及重置时间；说明类似“3/100”究竟表示已用还是剩余。资源不足时给出符合用户语言和权益的下一步，保留可恢复的输入或任务。前端显示、服务端判断、会员资格和充值入口保持一致，不把内部错误直接展示给用户。
- **成本和问题能否查清**：分别解释用户资源变化与供应商调用/成本，不拿请求数冒充成功产出数。按需要关联业务操作、发放、消费、释放与补偿记录；复用现有诊断能力，不默认搭建新账务或监控平台，不记录密钥或敏感内容。

## 如何验证

用现有测试身份和可控环境走通本次相关链路：取得资源 → 查询可用量 → 完成操作 → 读回结果及资源变化 → 核对管理侧或记录。补测本次会影响的失败恢复、重复执行、并发、到期/重置、越权和策略变更；界面提示成功不能替代余额、实际权益或最终产出的核对。

无法安全制造的外部故障可以用沙箱或模拟补充，说明替代了哪一环，不宣称验证了真实扣费。生产发放、撤销、扣款和配置变更须有对应授权，测试账号不等于无风险。验收请求不自动授权修复；修复与性能优化中的诊断盲区按需组合 `$open-vibecoding-diagnostic-readiness`。

## 组合与边界

产品侧判断规则与价值；交互侧解释状态与恢复路径；研发侧实现一致的规则与运营配套；测试侧核对最终结果。相关业务示例见 [场景示例](references/business-scenarios.md)，仅帮助理解，不作为默认规格。

沿用 Agent 自身的拆解方式。已明确且在实现范围内的必要配套应随功能落实；会改变收费承诺、资源归属或显著扩大范围的选择需确认。只要求分析时给出发现和缺口，不修改业务系统。不要求额外生成 PRD、change、tasks、方案报告或固定数据表，也不为普通功能引入整套计费架构。
